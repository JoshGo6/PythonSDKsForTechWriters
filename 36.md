Now I will present the lesson.# Lesson 36: curl vs SDK Calls — Reading Raw API Behavior

You now understand the vocabulary of HTTP requests and responses.  
But SDK documentation often shows you a clean `repo.name` and not the raw `curl` command that produced it.  
This lesson bridges that gap: you’ll learn how to read a `curl` invocation, interpret the raw JSON the API sends back, and see how an SDK (like PyGithub) turns that JSON into convenient Python attributes.  
The exercise at the end will have you parse a real-looking JSON response and produce a documentation‑style explanation.

---

## 1. Terminology and Theory

**curl**  
A command‑line tool for transferring data using HTTP. Developers use it to test APIs quickly.  
Think of it as a “raw request viewer”.

**REST API endpoint**  
A URL that represents a resource (like a repository or an issue).  
`curl https://api.github.com/repos/octocat/Hello-World` hits the **repos** endpoint.

**Raw API response**  
The HTTP response body, typically a JSON string, returned from an endpoint.  
Example (abbreviated):
```json
{
  "full_name": "octocat/Hello-World",
  "stargazers_count": 123,
  "open_issues_count": 5
}
```

**SDK abstraction**  
A Python library that wraps the REST API so you can write `repo.full_name` instead of memorising endpoint URLs and parsing JSON yourself.  
Under the hood, the SDK still performs HTTP requests – it just **hides** the HTTP details and **exposes** useful objects.

**Pagination**  
When a resource has many items (e.g., hundreds of repositories), the API breaks the response into **pages**.  
The raw response includes a `Link` header with the URL of the next page.  
SDKs like PyGithub handle pagination for you, turning the pages into a seamless iterable.

**What’s preserved vs hidden**  
- **Preserved:** The data fields (repo name, star count, etc.) – you see the same values.  
- **Hidden:** Status codes, headers, raw JSON structure – the SDK handles these for you.

> [!tip]  
> When you document an SDK, you explain the **object attributes**. When you document a raw API, you explain the **endpoint and JSON fields**. Understanding both makes you a better technical writer.

## 2. Syntax Section

### curl patterns

A typical `curl` call for a GitHub API:

```bash
curl -H "Authorization: Bearer $TOKEN" https://api.github.com/user
```

- `-H "Authorization: ..."` includes an authentication header.
- No `-X` flag means it uses the default `GET` method.
- To see the response headers (where pagination info lives), add `-i`:
  ```bash
  curl -i https://api.github.com/users/octocat/repos
  ```

### Parsing the raw JSON in Python

You already know `json.loads()`, which turns a JSON string into a Python dict/list structure.

```python
import json

raw_string = '{"full_name": "octocat/Hello-World"}'
data = json.loads(raw_string)
print(data["full_name"])   # "octocat/Hello-World"
```

Remember: a JSON object becomes a Python dict, a JSON array becomes a list, and string/number/boolean stay the same.

### Reading environment variables (from Lesson 31)

```python
import os
verbose = os.getenv("VERBOSE_OUTPUT") == "1"
if verbose:
    print("Extra detail…")
```

## 3. Worked Examples

### Example 1: curl returns a user object

Assume we ran:

```bash
curl https://api.github.com/users/octocat
```

and received this JSON string (saved as a multi‑line string in our script):

```python
import json

response = """
{
  "login": "octocat",
  "id": 583231,
  "name": "The Octocat",
  "public_repos": 8,
  "html_url": "https://github.com/octocat"
}
"""

data = json.loads(response)
print(f"{data['login']} ({data['name']}) has {data['public_repos']} public repos.")
```

Output:
```
octocat (The Octocat) has 8 public repos.
```

Now compare this to a hypothetical SDK call:

```python
# hypothetical SDK (doesn't exist yet)
user = github.get_user("octocat")
print(f"{user.login} ({user.name}) has {user.public_repos} repos.")
```

Both produce the same information – the SDK hides the raw HTTP call and the JSON parsing.

### Example 2: Raw pagination headers

When the response is paginated, `curl -i` shows the `Link` header:

```
HTTP/2 200
...
Link: <https://api.github.com/user/583231/repos?page=2>; rel="next"
```

The SDK (PyGithub) usually takes care of pagination for you; you just write a `for` loop.  
As a docs writer, you need to know that pagination exists and that the user might hit rate limits when many pages are fetched.

In raw `curl`, to get the next page you would extract the URL from the `Link` header and call it again.  
We won’t implement that here, but it’s important to recognise when you see it in API documentation.

### Example 3: Mapping raw JSON to SDK attributes

Raw JSON from `/repos/octocat/Hello-World`:
```json
{
  "full_name": "octocat/Hello-World",
  "description": "My first repository on GitHub!",
  "stargazers_count": 12,
  "open_issues_count": 2,
  "topics": ["octocat", "hello-world"]
}
```

In PyGithub (later), you would access it as:

```python
repo = g.get_repo("octocat/Hello-World")
print(repo.full_name)          # "octocat/Hello-World"
print(repo.description)        # "My first repository on GitHub!"
print(repo.stargazers_count)   # 12
print(repo.open_issues_count)  # 2
print(repo.get_topics())       # ["octocat", "hello-world"]
```

Notice that the attribute names are almost identical. The SDK **preserves** the data names but **hides** the fact that every attribute access may trigger an HTTP request under the hood.

## 4. Quick Reference

```python
# Parse a JSON string into a dict
import json
raw = '{"key": "value"}'
data = json.loads(raw)

# Access a value safely
name = data.get("name", "unknown")

# Print a doc-style summary
print(f"User {data['login']} has {data['public_repos']} repos.")

# Read an environment variable to control output
import os
if os.getenv("VERBOSE") == "1":
    print(json.dumps(data, indent=2))
```
